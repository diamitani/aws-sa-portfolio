LP 11 AWS Leadership Principle

Bias for Action

"Speed matters in business. Many decisions and actions are reversible and do not need extensive study. We value calculated risk taking."

S Situation

Our n8n instance was running daily workflow executions in production, and some were silently failing.

⚠️ There was no process in place to catch these failures proactively—someone would only notice a broken workflow once it caused a downstream problem, by which point revenue-generating automations had already been down for hours or days.
T Task

Without being asked, I decided to build a monitoring solution rather than wait for a failure to become visible enough that leadership requested one.

I set out to create a Claude skill and a corresponding n8n workflow that would automatically audit every execution daily and flag failures with a proposed fix, so we'd catch broken automations the same day they broke instead of discovering them reactively.

A Action
01

Two-Way Door Decision

Rather than spend weeks scoping a perfect monitoring platform, I moved on the simplest version that would work and treated it as a two-way door I could iterate on.

02

Skill Bootstrapping

Reused a skill I'd already built, n8n Engineer, to accelerate building a new one from a prompt rather than starting from zero.

03

Architecture Design

Gave it a lightweight project plan, architecture, and PRD, and had it connect to our n8n instance through a custom MCP and API integration to pull every workflow and execution, node by node, and output the results as both a spreadsheet and a written report—with the option to scan everything or target a specific workflow by ID or URL.

04

Immediate Production Use

Once that skill, n8n-execution-analyst, was working, I immediately used it to build the actual production workflow rather than treating the skill as a standalone experiment: a daily job that pulls all active executions from the prior day, generates a status table and root-cause analysis for any failures, and sends the report to the VP of Growth.

05

Ship, Don't Sequence

Shipped this in a single build cycle instead of separating skill-building and workflow-deployment into sequential phases, since a working daily report—even an imperfect one—was more valuable immediately than a more polished version delivered later.

R Result
Daily Automated Audit
<24h Failure Detection
Auto Root-Cause Analysis

RevOps and Growth now get a daily audit of every active n8n workflow, complete with failure analysis and suggested fixes, without anyone having to ask for it or manually investigate.

This turned workflow failures from something we discovered days later, often after they'd already broken a downstream process, into something caught and diagnosed within 24 hours—cutting the turnaround time between a workflow breaking and a fix being redeployed.

The Two-Way Door in Action:

Because I built and shipped it as a working first version rather than over-engineering it upfront, I was able to start learning from real daily reports immediately and can still iterate on the report format or add new checks without disrupting what's already in production.
